# 讲解页研究笔记与 Reduce 流程

生成 `explainer.mdx` 前必须先完成这个流程。目标不是写一篇摘要，而是产出一篇能让中文读者理解论文 **问题、思想、机制、实现细节、算法流程、实验结果、局限和复用方式** 的深度讲解。

讲解页必须来自 TeX 证据和逐步阅读。禁止只读 abstract、`paper.json`、现成摘要或脚本预览后直接写正文。

## 总体质量目标

`explainer.mdx` 应该像一篇高质量中文论文导读，而不是论文卡片扩写：

- **足够丰富**：普通论文讲解正文通常不少于 8,000 个中文字符；方法复杂、含算法/多实验表格/长附录的论文通常不少于 12,000 个中文字符。这里不把代码块和原文算法当作正文字符数。
- **足够具体**：必须讲清楚核心变量、数据结构、模块分工、算法步骤、训练/推理/搜索/评测流程，以及这些设计为什么能改善结果。
- **足够忠实**：每个主张都能回到论文某个 section、公式、图、表、算法、附录 prompt、代码或实验数字。
- **足够可用**：读者看完应能复述论文方法，知道如何粗略实现，知道结果怎么看，也知道哪些场景不适合直接套用。

不要为了显得长而堆砌空话。每一段都要服务理解：解释一个概念、拆一个机制、读一个结果、指出一个边界，或给一个工程迁移锚点。

## 临时笔记位置

在正式写 `explainer.mdx` 前，创建临时研究笔记：

```text
.tmp/paper-to-site/{slug}/explainer-notes.md
```

这个文件是工作过程产物，不进入前端、不复制到 `public/`，也不要在 `explainer.mdx` 里提到它。

## 第 0 步：建立内容清单

先扫描入口 TeX、所有 `\input` / `\include` 文件、附录、图片目录和已生成的 `reading.json`。在笔记开头写 `## Content Inventory`，列出讲解页必须覆盖的材料：

```md
## Content Inventory

### Sections
- Abstract:
- Introduction:
- Related Work:
- Method:
- Experiments:
- Limitations / Ethics:
- Appendix:

### Figures
- Figure 1 / 文件名：
- Figure 2 / 文件名：

### Tables
- Table 1：
- Table 2：

### Equations
- Eq. 1：
- Eq. 2：

### Algorithms
- Algorithm 1：
- Algorithm 2：

### Code / Prompt / Data Artifacts
- Listing / prompt / JSON / operator code：

### Experiment Assets
- 数据集：
- 指标：
- 基线：
- 主结果：
- 消融：
- 成本/效率：
- 人工评测或案例：
```

硬约束：

- `reading.json` 中出现的 `kind: "algorithm"`、`kind: "equation"`、`kind: "figure"`、`kind: "table"` 必须进入清单。
- TeX 附录中的 prompt、代码、算法、示例、数据构造细节不能因为“不在正文”而跳过。
- 如果某个图表或算法不适合进入最终讲解页，必须在 `Coverage Decision Log` 里写清楚理由，例如“重复展示同一趋势”“只服务排版示例”“过长且已用等价伪代码解释”。不能沉默漏掉。

## 第 1 步：章节扫描

在笔记里写结构地图：

```md
# Explainer Notes: {paper title}

## 结构地图

- Abstract: 核心问题、方法、结果、边界。
- Introduction: 动机、已有方法不足、贡献。
- Related Work: 论文把自己放在哪些研究线中。
- Method / Approach: 模块、公式、算法、数据结构、训练或推理流程。
- Experiments: 任务、指标、基线、主结果、消融、成本、案例。
- Limitations / Ethics / Appendix: 边界、实现细节、prompt、代码、补充实验。
```

结构地图必须覆盖正文和附录。不要把 appendix 当作可选材料；Agent 论文的关键实现细节、prompt、operator、评估协议和案例常常藏在附录里。

## 第 2 步：逐节阅读并记录证据

按论文顺序阅读 TeX。每读一个 section/subsection，就在笔记里填下面模板。不要只写“本节介绍方法”这种空话；每项都要包含论文证据或定位。

```md
## Section: {section title}

### 这节解决什么问题
- 用 3-6 句话说明本节在论文论证链里的作用。

### 论文主张与证据
- 主张：
  - 证据位置：section / figure / table / equation / algorithm / appendix。
  - 原因：为什么该证据能支撑这个主张。

### 机制卡片
- 名称：
- 输入：
- 输出：
- 中间状态 / 数据结构：
- 关键变量：
- 约束或假设：
- 运行顺序：
- 为什么这样设计有效：
- 实现时容易误解：
- 讲解页应放在哪个主线章节：

### 公式卡片
- 公式：
- 变量含义：
- 优化目标或约束：
- 直觉解释：
- 和算法/实验的关系：
- 讲解页是否使用 MathBlock：

### 算法卡片
- 算法名：
- 原文算法来源：
- 输入 / Require：
- 输出 / Ensure：
- 初始化：
- 主循环：
- 关键分支：
- 状态更新：
- 终止条件：
- 返回值：
- 需要在讲解页展示的原文或精简伪代码：
- AlgorithmBlock 后必须解释的 3-6 个步骤：

### 图表与代码
- Figure/Table/Algorithm/Listing/Prompt：文件名、caption 或 TeX 位置。
- 图表展示什么：
- 读者应如何读：
- 讲解页使用方式：FigureBlock / AlgorithmBlock / MathBlock / 代码块 / 文字解读。

### 实验与证据
- 任务/数据集：
- 指标含义：
- 基线：
- 数字结果：
- 消融变量：
- 成本或效率：
- 作者想证明什么：
- 读者该如何解读：
- 可能的反例或边界：

### 可复用启发
- 可以迁移到 agent 工程的结构、日志、评估、搜索、prompt 或数据处理方法。

### 还不清楚的问题
- 需要回看 TeX、图、表、算法或 appendix 的点。
```

记录要求：

- 把“论文怎么说”和“你的解释”分开。
- 不要大段复制原文；只摘关键短语、公式、图表编号、算法步骤、数据数字和证据位置。
- 对关键机制必须写“输入-处理-输出-反馈/状态更新”链条。
- 对实验必须写指标含义和结论边界，不能只写“效果更好”。

## 第 3 步：建立四个账本

完成逐节笔记后，在 `explainer-notes.md` 中追加四个账本。它们决定最终讲解页是否完整。

### 3.1 Mechanism Ledger

```md
## Mechanism Ledger

| 机制 | 解决的问题 | 输入 | 输出 | 关键变量/状态 | 证据 | 讲解章节 |
| --- | --- | --- | --- | --- | --- | --- |
```

必须覆盖论文核心方法中的所有主要模块。Agent 论文通常包括 workflow 表示、planner、memory、retriever、tool router、executor、evaluator、search tree、critic、reflection、multi-agent role 等。实际写哪些由论文决定，但不能只写一个总括词。

### 3.2 Algorithm Ledger

```md
## Algorithm Ledger

| 算法 | 是否进入讲解页 | 展示方式 | 必须解释的步骤 | 不展示理由 |
| --- | --- | --- | --- | --- |
```

硬约束：

- 如果论文或 `reading.json` 有算法块，讲解页必须至少包含 1 个 `<AlgorithmBlock />`。
- 如果有多个核心算法，优先展示最能解释论文方法闭环的算法；其余算法也必须在正文解释，或在账本中说明为什么不展示。
- `<AlgorithmBlock />` 不能孤立出现。它前面必须有一段说明算法要解决什么问题，后面必须有 2-5 段拆解输入、循环、分支、状态更新、评估/回传和终止条件。

### 3.3 Figure/Table Ledger

```md
## Figure/Table Ledger

| 图表 | 类型 | 讲什么 | 是否展示 | 读图/读表重点 | 对应讲解章节 |
| --- | --- | --- | --- | --- | --- |
```

硬约束：

- 至少展示 2 张核心图，除非论文只有 0-1 张图；这种情况必须说明并考虑生成一张中文辅助图。
- 主要实验表格必须被解释。可以不完整重排表格，但必须讲清楚指标、基线、主要数字、趋势和作者想证明什么。
- 图不能只贴 caption；正文必须解释图里模块之间的关系。

### 3.4 Results Ledger

```md
## Results Ledger

| 问题 | 数据集/任务 | 指标 | 最强基线 | 论文方法结果 | 提升/差异 | 解释 | 边界 |
| --- | --- | --- | --- | --- | --- | --- | --- |
```

硬约束：

- 主结果、消融、成本/效率/人工评测/案例中，至少覆盖 3 类证据；如果论文没有其中某类，写明不存在。
- 实验章节必须解释“指标为什么能衡量目标”，以及“结果支撑了哪个方法主张”。

## 第 4 步：生成 Reduce Plan 与讲解大纲

先写 `## Reduce Plan` 和 `## Explainer Outline`，再写 MDX。第 4 步的产物不是正文，而是可检查的讲解结构。

```md
## Reduce Plan

### 读者路径
1. 读者先理解的问题：
2. 然后理解的核心直觉：
3. 再进入的方法结构：
4. 再拆解的算法/实现细节：
5. 然后阅读实验结果：
6. 最后用局限和复用方式收束：

### 讲解页主线章节
- 读前先抓住结论：来自哪些笔记条目。
- 问题背景：来自哪些笔记条目。
- 方法总览：来自哪些机制卡片、图和公式。
- 核心机制一：来自哪些公式、算法、图、代码。
- 核心机制二：来自哪些公式、算法、图、代码。
- 算法与实现细节：来自哪些 Algorithm Ledger / appendix / code。
- 实验结果怎么读：来自哪些表和数字。
- 消融、案例与成本：来自哪些实验资产。
- 局限与复用启发：来自哪些限制、伦理、附录。

### 必须使用的资源
- FigureBlock：
- MathBlock：
- AlgorithmBlock：
- StepFlow / SplitBlock / ConceptTabs：
- code block：
- 实验数字或表格解读：
```

然后写 `## Explainer Outline`：

```md
## Explainer Outline

1. `## {主线章节标题}`
   - 目标：这一节要帮读者解决什么理解问题。
   - 内容来源：来自哪些 section、figure、table、algorithm 或 appendix。
   - 必讲概念：
   - 子节：需要时列出 0-4 个 `###`；不需要就写“无”。
   - 组件：计划使用哪些 FigureBlock、MathBlock、AlgorithmBlock、StepFlow、SplitBlock、ConceptTabs 或 code block。
   - 预计正文深度：短 / 中 / 长。
```

大纲硬约束：

- 通常使用 7-10 个 `##` 主线章节。
- 如果论文有算法，必须有一个主线章节或长子节专门讲算法/实现细节。
- 如果论文有实验，必须有一个主线章节专门讲实验主结果，另一个段落或章节讲消融、成本、案例或人工评测。
- `##` 不能机械复制论文目录；要按读者理解路径重组。

## 第 5 步：逐节生成 explainer.mdx

写作时遵循 `content-format.md` 和 `SKILL.md` 的 MDX 协议，并严格按 `Explainer Outline` 逐节生成正文。

生成方式：

1. 先写一个 `##` 章节，不要一次性展开整篇。
2. 对照该章节的目标、来源、必讲概念和组件。
3. 写完一节后，检查它是否回答了“为什么、怎么做、为什么有效、证据是什么、读者能带走什么”。
4. 再进入下一节。
5. 如果写作过程中发现大纲不合理，先回到 `Explainer Outline` 修改结构，再继续写正文。

### 章节深度要求

- `## 读前先抓住结论`：3-5 段。必须说明一句话问题、核心方法、最重要结果、适用边界，不要只有摘要。
- `## 问题背景`：4-7 段。必须解释已有方法为什么不够、论文切入点和 agent 领域关系。
- 方法相关章节：每个核心机制通常 5-10 段。必须包含变量/模块、输入输出、执行顺序、反馈信号、图或公式证据。
- 算法章节：必须包含 `<AlgorithmBlock />` 或等价代码块，并在前后解释算法阶段。
- 实验章节：通常 6-10 段。必须解释数据集、指标、基线、主结果、消融/成本/案例和结论边界。
- 局限章节：3-6 段。必须指出失败场景、依赖假设和工程复用时的调整方式。

### 核心机制写法

每个核心机制都按这个顺序展开：

1. 它解决什么具体困难。
2. 论文用了什么结构、公式、数据结构或算法。
3. 它运行时输入、输出和中间状态是什么。
4. 它如何和其他模块交互。
5. 为什么这个设计可能有效。
6. 哪个图、表、算法、消融或 appendix 细节支持它。
7. 读者复用时要注意什么边界。

### 算法写法

如果论文正文或附录有核心算法环境（例如 `algorithm`、`algorithmic`、`algorithm2e`），讲解页应优先使用 `<AlgorithmBlock />` 展示原文算法步骤。只有当算法非常长、完整展示会压垮阅读节奏时，才节选核心步骤，但必须说明该算法来自论文原文。

算法讲解必须包含：

- 算法要解决的问题。
- Require / input 和 Ensure / output。
- 初始化状态是什么。
- 主循环每轮做什么。
- 选择、扩展、生成、检索、评估、更新、回传等阶段各自作用。
- 关键条件分支如何影响行为。
- 终止条件和返回值。
- 它与论文结果或消融的关系。

禁止只写“这段算法展示整体流程”。这不是解释。

### 实验写法

实验章节必须回答：

- 论文用哪些任务验证方法，为什么这些任务能覆盖论文目标。
- 每个指标是什么意思，越高越好还是越低越好。
- 主要基线代表什么类型的方法。
- 主结果显示了什么趋势，不只是哪个数字最大。
- 消融实验拆掉了什么，说明哪个设计有用。
- 成本/效率/人工评测/案例分析如何补充主结果。
- 结果的边界是什么：数据规模、任务类型、评估函数、模型依赖、成本、人工标注或安全风险。

## 第 6 步：自检与补齐

写完 `explainer.mdx` 后，回到 `explainer-notes.md` 做覆盖矩阵：

```md
## Coverage Check

- [ ] Abstract 的问题、方法、结果、边界都进入讲解页。
- [ ] Introduction 的动机和现有方法不足被解释清楚。
- [ ] Related Work 不只是罗列引用，而是说明论文相对位置。
- [ ] Method 的核心模块、公式、算法、数据结构和关键变量都被解释。
- [ ] 每个核心机制都有“问题-结构-运行-证据-边界”解释链。
- [ ] 核心算法以 AlgorithmBlock 或等价伪代码形式展示，并紧跟逐步中文讲解。
- [ ] 每个 Algorithm Ledger 条目都有展示、解释或不展示理由。
- [ ] 每个核心图表至少被展示或解释一次。
- [ ] 实验任务、指标、基线、主结果、消融、成本或案例被解释，而不是只复述数字。
- [ ] 附录中的关键 prompt、算法、代码、数据构造或案例没有漏掉。
- [ ] 局限、失败场景或适用边界被说明。
- [ ] 讲解页正文足够丰富，不是短摘要；方法和实验章节都有连续解释。
- [ ] 讲解页没有“生成记录”“由 skill 生成”“后续补充”等制作说明。
- [ ] 讲解页没有无来源的夸大评价，也没有伪造实验数据。
```

如果有任一项不满足，先补 `explainer-notes.md`，再修改 `explainer.mdx`。不要用一句泛泛总结代替缺失章节。

## 第 7 步：运行质量脚本

生成或更新讲解页后运行：

```bash
node .agents/skills/paper-to-site/scripts/check-explainer-quality.mjs
```

脚本失败时，必须按错误提示补讲解页或研究笔记，而不是降低脚本门槛。只有当脚本规则与论文事实冲突时，才修改脚本，并在提交说明里解释原因。

## 常见失败模式

- 只读 abstract 就开始写，导致方法章节空泛。
- 目录大标题太少，全文像摘要；或标题太多，变成术语堆砌。
- 算法块没有引用，或者引用后不解释每个阶段。
- 实验章节只写“效果更好”，没有解释指标、基线和趋势。
- 使用论文图但不解释图里每个模块的含义。
- 写了公式但没有解释变量、目标和直觉。
- 把 appendix 的 prompt、算法、代码、案例漏掉。
- 只有“论文提出了 X”这种句式，没有实现直觉和工程复用。
- 讲解页出现开发过程说明。
