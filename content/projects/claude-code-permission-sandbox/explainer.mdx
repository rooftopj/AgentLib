# Claude Code 源码解析（05）Permission / Sandbox：工具权限、用户批准与命令隔离

## 先给结论

Claude Code 的安全机制不是一个“执行前问一下用户”的 if。它分成两层：Permission 决定一次 tool call 是否可以继续，Sandbox 决定 Bash 这类 shell 命令是否要包进受限执行环境。

## 工具调用先进入统一执行器

`services/tools/toolExecution.ts` 是读这条线的入口。模型吐出 tool use 后，`runToolUse()` 先找到工具定义、校验输入，然后进入 `streamedCheckPermissionsAndCallTool()`。

```ts
// assets/projects/claude-code/src/services/tools/toolExecution.ts
for await (const update of streamedCheckPermissionsAndCallTool(
  tool,
  toolUse.id,
  toolInput,
  toolUseContext,
  canUseTool,
  assistantMessage,
  messageId,
  requestId,
  mcpServerType,
  mcpServerBaseUrl,
)) {
  yield update
}
```

真正执行前还有 PreToolUse hook。hook 可以补充消息、改 input、阻止继续，或者直接给出 permission result。之后才进入 `resolveHookPermissionDecision()`，把 hook 结果和 `canUseTool` 合并成一次最终权限决策。

```ts
// assets/projects/claude-code/src/services/tools/toolExecution.ts
const resolved = await resolveHookPermissionDecision(
  hookPermissionResult,
  tool,
  processedInput,
  toolUseContext,
  canUseTool,
  assistantMessage,
  toolUseID,
)
const permissionDecision = resolved.decision
```

## Permission Context 是决策语言

`Tool.ts` 里的 `ToolPermissionContext` 把权限状态压成一个对象。它不是只有 `mode`，还包括额外工作目录、always allow/deny/ask 三类规则、bypass 可用性、异步 agent 是否应避免弹窗等。

```ts
// assets/projects/claude-code/src/Tool.ts
export type ToolPermissionContext = DeepImmutable<{
  mode: PermissionMode
  additionalWorkingDirectories: Map<string, AdditionalWorkingDirectory>
  alwaysAllowRules: ToolPermissionRulesBySource
  alwaysDenyRules: ToolPermissionRulesBySource
  alwaysAskRules: ToolPermissionRulesBySource
  isBypassPermissionsModeAvailable: boolean
  shouldAvoidPermissionPrompts?: boolean
  awaitAutomatedChecksBeforeDialog?: boolean
  prePlanMode?: PermissionMode
}>
```

`PermissionMode.ts` 给这些 mode 加上产品语义：`default`、`plan`、`acceptEdits`、`bypassPermissions`、`dontAsk`，以及 feature-gated 的 `auto`。这解释了为什么“模式”不是简单布尔值。

```ts
// assets/projects/claude-code/src/utils/permissions/PermissionMode.ts
const PERMISSION_MODE_CONFIG = {
  default: { title: 'Default', external: 'default' },
  plan: { title: 'Plan Mode', external: 'plan' },
  acceptEdits: { title: 'Accept edits', external: 'acceptEdits' },
  bypassPermissions: { title: 'Bypass Permissions', external: 'bypassPermissions' },
  dontAsk: { title: "Don't Ask", external: 'dontAsk' },
}
```

## 主闸口的顺序决定安全边界

`hasPermissionsToUseToolInner()` 的顺序非常关键。它先看整个工具是否被 deny，再看 ask，然后调用工具自己的 `checkPermissions()`。这一步会让 Bash、FileWrite、MCP 等工具各自做局部判断。

```ts
// assets/projects/claude-code/src/utils/permissions/permissions.ts
const denyRule = getDenyRuleForTool(appState.toolPermissionContext, tool)
if (denyRule) return { behavior: 'deny', decisionReason: { type: 'rule', rule: denyRule } }

const askRule = getAskRuleForTool(appState.toolPermissionContext, tool)
if (askRule) {
  const canSandboxAutoAllow =
    tool.name === BASH_TOOL_NAME &&
    SandboxManager.isSandboxingEnabled() &&
    SandboxManager.isAutoAllowBashIfSandboxedEnabled() &&
    shouldUseSandbox(input)
  if (!canSandboxAutoAllow) return { behavior: 'ask', decisionReason: { type: 'rule', rule: askRule } }
}

toolPermissionResult = await tool.checkPermissions(parsedInput, context)
```

工具自检之后，源码继续检查几类“不能被 bypass 轻易越过”的结果：工具返回 deny、需要用户交互、内容级 ask rule、safety check。然后才处理 `bypassPermissions` 和 always allow。

```ts
// assets/projects/claude-code/src/utils/permissions/permissions.ts
if (toolPermissionResult?.behavior === 'deny') return toolPermissionResult
if (tool.requiresUserInteraction?.() && toolPermissionResult?.behavior === 'ask') return toolPermissionResult
if (
  toolPermissionResult?.behavior === 'ask' &&
  toolPermissionResult.decisionReason?.type === 'safetyCheck'
) {
  return toolPermissionResult
}

const shouldBypassPermissions =
  appState.toolPermissionContext.mode === 'bypassPermissions' ||
  (appState.toolPermissionContext.mode === 'plan' &&
    appState.toolPermissionContext.isBypassPermissionsModeAvailable)
if (shouldBypassPermissions) return { behavior: 'allow', decisionReason: { type: 'mode', mode: appState.toolPermissionContext.mode } }
```

## Bash 是最复杂的工具级判断

Bash 的 `checkPermissions()` 只是转发到 `bashToolHasPermission()`。复杂度都藏在 `bashPermissions.ts`：它要处理 exact rule、prefix rule、compound command、重定向、路径约束、sed 约束、read-only 命令、命令注入检查和 sandbox auto-allow。

```ts
// assets/projects/claude-code/src/tools/BashTool/BashTool.tsx
async checkPermissions(input, context): Promise<PermissionResult> {
  return bashToolHasPermission(input, context)
}
```

规则匹配的一个核心设计是：allow 要保守，deny/ask 要更难绕过。源码会对 deny/ask 做更 aggressive 的 env var stripping，避免 `FOO=bar rm ...` 绕开 `Bash(rm:*)`。

```ts
// assets/projects/claude-code/src/tools/BashTool/bashPermissions.ts
const matchingDenyRules = filterRulesByContentsMatchingInput(
  input,
  denyRuleByContents,
  matchMode,
  { stripAllEnvVars: true, skipCompoundCheck: true },
)

const matchingAllowRules = filterRulesByContentsMatchingInput(
  input,
  allowRuleByContents,
  matchMode,
  { skipCompoundCheck },
)
```

compound command 也不能只看整串命令。`checkSandboxAutoAllow()` 里会拆子命令，先扫每个 subcommand 的 deny/ask。这样 `echo ok && rm -rf /` 不会因为整串看起来不以 `rm` 开头而绕过。

```ts
// assets/projects/claude-code/src/tools/BashTool/bashPermissions.ts
const subcommands = splitCommand(command)
if (subcommands.length > 1) {
  for (const sub of subcommands) {
    const subResult = matchingRulesForInput(
      { command: sub },
      toolPermissionContext,
      'prefix',
    )
    if (subResult.matchingDenyRules[0] !== undefined) {
      return { behavior: 'deny', decisionReason: { type: 'rule', rule: subResult.matchingDenyRules[0] } }
    }
  }
}
```

## Sandbox 只在合适的 Bash 路径生效

`shouldUseSandbox()` 是一个很好的边界说明。只有 sandbox enabled、命令没有显式危险 override、存在 command、并且不命中 excludedCommands 时，才返回 true。

```ts
// assets/projects/claude-code/src/tools/BashTool/shouldUseSandbox.ts
export function shouldUseSandbox(input: Partial<SandboxInput>): boolean {
  if (!SandboxManager.isSandboxingEnabled()) return false
  if (
    input.dangerouslyDisableSandbox &&
    SandboxManager.areUnsandboxedCommandsAllowed()
  ) {
    return false
  }
  if (!input.command) return false
  if (containsExcludedCommand(input.command)) return false
  return true
}
```

源码注释明确说 `excludedCommands` 是用户便利功能，不是安全边界。真正的安全控制仍然是 permission prompt 和 sandbox runtime；如果命令选择不进 sandbox，就应该重新落回权限审批。

## Sandbox Config 从规则翻译而来

`sandbox-adapter.ts` 把 Claude Code 的 settings 和 permission rules 翻译成 `@anthropic-ai/sandbox-runtime` 的配置。这里最关键的是：权限规则不仅影响 app 层审批，也会影响执行层可访问的域名和路径。

```ts
// assets/projects/claude-code/src/utils/sandbox/sandbox-adapter.ts
export function convertToSandboxRuntimeConfig(
  settings: SettingsJson,
): SandboxRuntimeConfig {
  const permissions = settings.permissions || {}
  const allowedDomains: string[] = []
  const deniedDomains: string[] = []
  const allowWrite: string[] = ['.', getClaudeTempDir()]
  const denyWrite: string[] = []
  const denyRead: string[] = []
  const allowRead: string[] = []
```

WebFetch 的 `domain:` allow/deny 会进入 sandbox network；Edit/Read 的规则会进入 filesystem allow/deny。除此之外，它还硬挡 settings 文件、managed settings drop-in、`.claude/skills` 和裸 git repo 植入路径。

```ts
// assets/projects/claude-code/src/utils/sandbox/sandbox-adapter.ts
for (const ruleString of permissions.allow || []) {
  const rule = permissionRuleValueFromString(ruleString)
  if (rule.toolName === WEB_FETCH_TOOL_NAME && rule.ruleContent?.startsWith('domain:')) {
    allowedDomains.push(rule.ruleContent.substring('domain:'.length))
  }
}

denyWrite.push(...settingsPaths)
denyWrite.push(getManagedSettingsDropInDir())
denyWrite.push(resolve(originalCwd, '.claude', 'skills'))
```

## 文件工具关注路径和竞态

文件工具不需要 Bash 那种命令语义分析，但它们有自己的风险：路径是否在工作目录内，是否命中 deny/ask/allow，是否是 `.git`、`.claude`、`.vscode` 这类危险路径，写入前文件是否被用户或 linter 改过。

```ts
// assets/projects/claude-code/src/utils/permissions/filesystem.ts
export function checkWritePermissionForTool<Input extends AnyObject>(
  tool: Tool<Input>,
  input: z.infer<Input>,
  toolPermissionContext: ToolPermissionContext,
): PermissionDecision {
  const path = tool.getPath(input)
  const pathsToCheck = getPathsForPermissionCheck(path)
  for (const pathToCheck of pathsToCheck) {
    const denyRule = matchingRuleForInput(pathToCheck, toolPermissionContext, 'edit', 'deny')
    if (denyRule) return { behavior: 'deny', decisionReason: { type: 'rule', rule: denyRule } }
  }
```

安全路径检查在 allow rule 之前。也就是说，普通 allow 不能随便越过 `.git`、`.claude/settings.json`、shell profile 等敏感位置。只有 session-scoped 的 `.claude/**` 特殊 allow 才能在严格范围内放行。

```ts
// assets/projects/claude-code/src/utils/permissions/filesystem.ts
const safetyCheck = checkPathSafetyForAutoEdit(path, pathsToCheck)
if (!safetyCheck.safe) {
  return {
    behavior: 'ask',
    message: safetyCheck.message,
    decisionReason: {
      type: 'safetyCheck',
      reason: safetyCheck.message,
      classifierApprovable: safetyCheck.classifierApprovable,
    },
  }
}
```

`FileWriteTool` 还要求写入已有文件前必须读过，并检查 mtime。这个机制防止模型基于过期视图覆盖用户或工具刚刚改过的内容。

```ts
// assets/projects/claude-code/src/tools/FileWriteTool/FileWriteTool.ts
const readTimestamp = toolUseContext.readFileState.get(fullFilePath)
if (!readTimestamp || readTimestamp.isPartialView) {
  return { result: false, message: 'File has not been read yet. Read it first before writing to it.' }
}
if (lastWriteTime > readTimestamp.timestamp) {
  return { result: false, message: 'File has been modified since read, either by the user or by a linter.' }
}
```

## 用户批准会变成 PermissionUpdate

当决策是 ask，交互 UI、SDK prompt、PermissionRequest hook 或 bridge 都可能给出结果。核心不是“用户点了 Yes”，而是批准可以携带 `PermissionUpdate`：加规则、改 mode、加目录，并选择 session 或 settings 级持久化。

```ts
// assets/projects/claude-code/src/utils/permissions/PermissionUpdate.ts
export function applyPermissionUpdate(
  context: ToolPermissionContext,
  update: PermissionUpdate,
): ToolPermissionContext {
  switch (update.type) {
    case 'setMode':
      return { ...context, mode: update.mode }
    case 'addRules':
      return {
        ...context,
        [ruleKind]: {
          ...context[ruleKind],
          [update.destination]: [
            ...(context[ruleKind][update.destination] || []),
            ...ruleStrings,
          ],
        },
      }
```

持久化和上下文更新是分开的。`session` rule 只影响当前会话；`localSettings`、`userSettings`、`projectSettings` 才会写回 settings。这个分层让“一次批准”和“以后都允许”在数据结构上可区分。

## MCP 和 WebFetch 不等于 Shell Sandbox

`MCPTool` 默认返回 passthrough，让外层权限系统继续决定。MCP 工具名还会按 server/tool 做匹配，例如 server 级 rule 可以覆盖该 server 下的工具。这和 Bash sandbox 是不同层。

```ts
// assets/projects/claude-code/src/tools/MCPTool/MCPTool.ts
export const MCPTool = buildTool({
  isMcp: true,
  name: 'mcp',
  async checkPermissions(): Promise<PermissionResult> {
    return {
      behavior: 'passthrough',
      message: 'MCPTool requires permission.',
    }
  },
})
```

WebFetch 的 domain rule 会同时出现在工具权限和 sandbox network config 的语境里，但语义仍要区分：WebFetch 自己是一个工具调用；sandbox network 限制的是被 sandbox 包住的进程能访问哪些网络。

## 可复用设计

Claude Code 这套设计最值得学的是分层：统一协议收口，局部工具负责风险判断，执行层 sandbox 作为另一道防线。这样系统能同时覆盖 Bash、文件工具、WebFetch、MCP，而不是把所有风险硬塞进一个全局规则表。

<ConceptTabs
  tabs="统一协议|局部判断|分级回写|执行隔离"
  panels="所有工具最后都返回 allow/ask/deny、message、suggestions、decisionReason 和可选 updatedInput，主执行器只消费统一结果。|Bash 看命令结构和路径，FileWrite 看文件状态和敏感路径，MCP 看 server/tool rule；风险知识放在最懂它的工具旁边。|PermissionUpdate 把 session 临时授权和 settings 持久授权分开，避免一次批准自然膨胀成永久规则。|sandbox 只负责它能负责的执行环境，不伪装成产品层权限，也不替 MCP server 做安全承诺。"
/>

一个很实用的工程原则是“强拒绝先于便利放行”。源码把 deny、ask rule、safety check 放在 bypass/acceptEdits 前面，说明 convenience mode 不是最高权力。

## 边界与风险

这套机制不是完整 VM，不是 git 权限模型，也不是所有外部能力的单点拦截器。尤其是 `dangerouslyDisableSandbox`、`allowUnsandboxedCommands`、MCP server、SDK bridge、hooks 都会引入额外边界。

<SplitBlock
  leftTitle="能相信的部分"
  left="一次 tool call 会集中形成 PermissionDecision；deny 和 safetyCheck 在顺序上强于普通模式放行；Bash sandbox 配置会从 settings 和 rules 翻译到 runtime。"
  rightTitle="不能误读的部分"
  right="sandbox 不包整个进程；excludedCommands 不是安全边界；WebFetch/MCP 不是自动进 shell sandbox；bypassPermissions 更接近少问权限，不是更强隔离。"
/>

如果要把这个设计搬到自己的 agent，关键不是复制这些规则名，而是复制职责边界：工具调用前先有统一决策协议，危险判断靠工具局部实现，用户授权要能区分临时和持久，命令执行再用独立 sandbox 做第二层约束。
