# Claude Code 源码解析（03）Context Management：动态注入、工具结果预算与多层压缩

## 先给结论

Claude Code 的上下文管理不是“快满了就总结一下”。它更像一套分层预算系统：固定 context 只放稳定信息，动态信息用 attachment 增量注入，工具结果先替换和持久化，仍然太大时再进入 microcompact、session memory compact 或 legacy compact。

## 先看证据地图

本文只讲“上下文怎么进模型、怎么被压缩”。不展开第一讲的长期 memory 写入，也不展开第二讲的 checkpoint restore。

```text
# 1 assets/projects/claude-code/src/context.ts
# 2 assets/projects/claude-code/src/query.ts
# 3 assets/projects/claude-code/src/utils/attachments.ts
# 4 assets/projects/claude-code/src/utils/toolResultStorage.ts
# 5 assets/projects/claude-code/src/services/compact/microCompact.ts
# 6 assets/projects/claude-code/src/services/compact/autoCompact.ts
# 7 assets/projects/claude-code/src/services/compact/compact.ts
# 8 assets/projects/claude-code/src/services/compact/sessionMemoryCompact.ts
```

质量门控上先说清楚：这里没有 vector storage、embedding search 或 LLM rerank。所谓 recall/search 主要是读取当前会话、文件状态、CLAUDE.md/nested memory 或 transcript 里的上下文记录，不是语义向量召回。

## 固定上下文只放稳定信息

`context.ts` 把上下文分成 `getSystemContext()` 和 `getUserContext()`。system context 里包括 git status 和 cache breaker；user context 里包括 CLAUDE.md/memory files 和日期。

```ts
// assets/projects/claude-code/src/context.ts
export const getSystemContext = memoize(async () => {
  const gitStatus =
    isEnvTruthy(process.env.CLAUDE_CODE_REMOTE) ||
    !shouldIncludeGitInstructions()
      ? null
      : await getGitStatus()
  return {
    ...(gitStatus && { gitStatus }),
    ...(injection ? { cacheBreaker: `[CACHE_BREAKER: ${injection}]` } : {}),
  }
})
```

`getUserContext()` 会决定是否读取 CLAUDE.md。`--bare` 和 `CLAUDE_CODE_DISABLE_CLAUDE_MDS` 都会影响这条路径；读取后的内容还会缓存，供 auto-mode classifier 等逻辑复用。

```ts
// assets/projects/claude-code/src/context.ts
const claudeMd = shouldDisableClaudeMd
  ? null
  : getClaudeMds(filterInjectedMemoryFiles(await getMemoryFiles()))

return {
  ...(claudeMd && { claudeMd }),
  currentDate: `Today's date is ${getLocalISODate()}.`,
}
```

## 动态注入不是拼大 prompt

`query.ts` 在工具调用结束后才处理 attachment。这样做很细：工具结果先被纳入历史，再追加“刚刚发生的变化”，避免把 queued command、文件变更、skill discovery、memory prefetch 混进静态 prompt。

```ts
// assets/projects/claude-code/src/query.ts
for await (const attachment of getAttachmentMessages(
  null,
  updatedToolUseContext,
  null,
  queuedCommandsSnapshot,
  [...messagesForQuery, ...assistantMessages, ...toolResults],
  querySource,
)) {
  yield attachment
  toolResults.push(attachment)
}
```

`attachments.ts` 里可以看到一组动态 attachment：queued commands、date change、deferred tools delta、agent listing delta、MCP instructions delta、changed files、nested memory、dynamic skill、plan mode、task reminder 等。

```ts
// assets/projects/claude-code/src/utils/attachments.ts
const allThreadAttachments = [
  maybe('queued_commands', () => getQueuedCommandAttachments(queuedCommands)),
  maybe('deferred_tools_delta', () =>
    Promise.resolve(getDeferredToolsDeltaAttachment(...))),
  maybe('agent_listing_delta', () =>
    Promise.resolve(getAgentListingDeltaAttachment(toolUseContext, messages))),
  maybe('mcp_instructions_delta', () =>
    Promise.resolve(getMcpInstructionsDeltaAttachment(...))),
  maybe('changed_files', () => getChangedFiles(context)),
  maybe('nested_memory', () => getNestedMemoryAttachments(context)),
]
```

## Delta 注入解决缓存破坏

很多看似应该放进工具描述的东西，被 Claude Code 移到了 attachment delta。典型例子是 agent listing：源码注释说 agent 列表放在工具描述里会造成大量 cache creation，因为 MCP 连接、插件重载、权限变化都会改变描述。

```ts
// assets/projects/claude-code/src/utils/attachments.ts
export function getAgentListingDeltaAttachment(toolUseContext, messages) {
  if (!shouldInjectAgentListInMessages()) return []
  const announced = new Set<string>()
  for (const msg of messages ?? []) {
    if (msg.type !== 'attachment') continue
    if (msg.attachment.type !== 'agent_listing_delta') continue
    for (const t of msg.attachment.addedTypes) announced.add(t)
    for (const t of msg.attachment.removedTypes) announced.delete(t)
  }
  return [{ type: 'agent_listing_delta', addedTypes, removedTypes }]
}
```

MCP instructions 也走 delta。它不是每轮塞全量说明，而是比较当前 MCP client/tool 与历史 attachment，只有变化才注入。

```ts
// assets/projects/claude-code/src/utils/attachments.ts
export function getMcpInstructionsDeltaAttachment(
  mcpClients,
  tools,
  model,
  messages,
) {
  const delta = getMcpInstructionsDelta(mcpClients, messages ?? [], clientSide)
  if (!delta) return []
  return [{ type: 'mcp_instructions_delta', ...delta }]
}
```

## Nested memory 有去重设计

CLAUDE.md 和 nested memory 的注入不是“读到就塞”。`memoryFilesToAttachments()` 同时用 `loadedNestedMemoryPaths` 和 `readFileState` 去重。注释里解释：`readFileState` 是 LRU，忙碌会话里可能淘汰；所以需要一个不淘汰的 Set 防止反复注入。

```ts
// assets/projects/claude-code/src/utils/attachments.ts
if (toolUseContext.loadedNestedMemoryPaths?.has(memoryFile.path)) {
  continue
}
if (!toolUseContext.readFileState.has(memoryFile.path)) {
  attachments.push({
    type: 'nested_memory',
    path: memoryFile.path,
    content: memoryFile,
  })
  toolUseContext.loadedNestedMemoryPaths?.add(memoryFile.path)
}
```

这里和第一讲 memory 的写入、remember、冲突/dedup 不同。它只负责“当前 turn 需要把哪些上下文放进模型”，不是更新长期记忆事实。

## 第一层压缩：工具结果预算

长上下文最容易爆的不是用户文本，而是工具结果。`toolResultStorage.ts` 先对大工具输出做 persistence：把完整内容写入 `tool-results` 目录，只把文件路径和预览留给模型。

```ts
// assets/projects/claude-code/src/utils/toolResultStorage.ts
export function getToolResultsDir(): string {
  return join(getSessionDir(), TOOL_RESULTS_SUBDIR)
}

export function buildLargeToolResultMessage(result) {
  return `<persisted-output>\n` +
    `Output too large. Full output saved to: ${result.filepath}\n\n` +
    `Preview:\n${result.preview}\n` +
    `</persisted-output>`
}
```

第二层是 aggregate tool result budget。它不是简单截断，而是记录每个 tool_use_id 的替换决策，resume 后也能复原同样的 replacement，避免 prompt cache 因模板变化或路径变化被破坏。

```ts
// assets/projects/claude-code/src/utils/toolResultStorage.ts
export type ContentReplacementState = {
  seenIds: Set<string>
  replacements: Map<string, string>
}

export type ContentReplacementRecord = {
  kind: 'tool-result'
  toolUseId: string
  replacement: string
}
```

## 第二层压缩：microcompact

`query.ts` 在 autocompact 前调用 microcompact。源码注释强调顺序：tool result budget 先跑，snip 再跑，microcompact 再跑，最后才是 autocompact。

```ts
// assets/projects/claude-code/src/query.ts
messagesForQuery = await applyToolResultBudget(...)
const snipResult = snipModule!.snipCompactIfNeeded(messagesForQuery)
const microcompactResult = await deps.microcompact(
  messagesForQuery,
  toolUseContext,
  querySource,
)
messagesForQuery = microcompactResult.messages
```

`microCompact.ts` 里有两条路径。time-based microcompact 在缓存已经冷掉时直接清理旧工具结果；cached microcompact 则使用 cache editing，尽量不改本地 message 内容。

```ts
// assets/projects/claude-code/src/services/compact/microCompact.ts
const timeBasedResult = maybeTimeBasedMicrocompact(messages, querySource)
if (timeBasedResult) return timeBasedResult

if (mod.isCachedMicrocompactEnabled() && isMainThreadSource(querySource)) {
  return await cachedMicrocompactPath(messages, querySource)
}
return { messages }
```

cached microcompact 的关键点是“不改本地消息，只生成 cache_edits”。这解释了为什么它能降低 token 压力，又尽量保持缓存前缀稳定。

```ts
// assets/projects/claude-code/src/services/compact/microCompact.ts
const toolsToDelete = mod.getToolResultsToDelete(state)
if (toolsToDelete.length > 0) {
  const cacheEdits = mod.createCacheEditsBlock(state, toolsToDelete)
  if (cacheEdits) pendingCacheEdits = cacheEdits
  return {
    messages,
    compactionInfo: { pendingCacheEdits: { trigger: 'auto', deletedToolIds } },
  }
}
```

## 第三层压缩：auto compact

autocompact 有明确阈值。它先从模型 context window 中扣掉摘要输出预算，再留出 `AUTOCOMPACT_BUFFER_TOKENS`。这意味着 compact 不是等完全爆掉才触发，而是提前给摘要生成留空间。

```ts
// assets/projects/claude-code/src/services/compact/autoCompact.ts
const MAX_OUTPUT_TOKENS_FOR_SUMMARY = 20_000
export const AUTOCOMPACT_BUFFER_TOKENS = 13_000

export function getAutoCompactThreshold(model: string): number {
  const effectiveContextWindow = getEffectiveContextWindowSize(model)
  return effectiveContextWindow - AUTOCOMPACT_BUFFER_TOKENS
}
```

它还带 circuit breaker。连续 autocompact 失败太多次，就停止继续烧 API 调用。这种失败恢复比“无限重试总结”重要得多。

```ts
// assets/projects/claude-code/src/services/compact/autoCompact.ts
const MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3
if (tracking?.consecutiveFailures >= MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES) {
  return { wasCompacted: false }
}
```

## Session memory compact 是优先尝试

autocompact 真正进入重压缩前，会先尝试 session memory compact。它不是再 fork 一个 summarizer，而是读取已经抽取好的 session memory 文件，生成 compact summary，再保留最近未总结的消息尾部。

```ts
// assets/projects/claude-code/src/services/compact/autoCompact.ts
const sessionMemoryResult = await trySessionMemoryCompaction(
  messages,
  toolUseContext.agentId,
  recompactionInfo.autoCompactThreshold,
)
if (sessionMemoryResult) {
  return { wasCompacted: true, compactionResult: sessionMemoryResult }
}
```

`sessionMemoryCompact.ts` 里有两个场景：正常会话按 `lastSummarizedMessageId` 找边界；resume 后如果边界未知，就保守地把 session memory 当 summary，并让后续逻辑决定保留哪些消息。

```ts
// assets/projects/claude-code/src/services/compact/sessionMemoryCompact.ts
if (lastSummarizedMessageId) {
  lastSummarizedIndex = messages.findIndex(
    msg => msg.uuid === lastSummarizedMessageId,
  )
} else {
  lastSummarizedIndex = messages.length - 1
}
const startIndex = calculateMessagesToKeepIndex(messages, lastSummarizedIndex)
const messagesToKeep = messages.slice(startIndex)
```

## legacy compact 会补回必要上下文

`compactConversation()` 不只是把旧消息变成摘要。它会先跑 PreCompact hook，再清 readFileState，然后把最近读取文件、异步 agent、plan、plan mode、invoked skills、tools delta、agent listing delta、MCP instructions delta、SessionStart hook 结果补回来。

```ts
// assets/projects/claude-code/src/services/compact/compact.ts
const [fileAttachments, asyncAgentAttachments] = await Promise.all([
  createPostCompactFileAttachments(preCompactReadFileState, context, 5),
  createAsyncAgentAttachmentsIfNeeded(context),
])

const planAttachment = createPlanAttachmentIfNeeded(context.agentId)
const skillAttachment = createSkillAttachmentIfNeeded(context.agentId)
```

这就是它精心的地方：compact 会删除大量历史，但不会假装 summary 能替代所有运行态上下文。被压掉的文件阅读、plan mode、skill 指令和工具变化，需要用 post-compact attachment 重建。

```ts
// assets/projects/claude-code/src/services/compact/compact.ts
for (const att of getDeferredToolsDeltaAttachment(context.options.tools, ...)) {
  postCompactFileAttachments.push(createAttachmentMessage(att))
}
for (const att of getAgentListingDeltaAttachment(context, [])) {
  postCompactFileAttachments.push(createAttachmentMessage(att))
}
```

## 边界与可复用设计

这套机制最值得复用的不是某个常量，而是顺序：先固定上下文，再动态增量；先局部替换，再局部压缩；最后才做全局摘要。这样能减少不必要的 token、避免 cache 失效，并让恢复后的模型仍然知道当前工具、文件、plan 和 skill 状态。

<CalloutBlock
  title="不要把上下文管理等同于摘要"
  body="摘要只是最后一层。真正影响体验的是前面的预算纪律：工具结果 storage、content replacement、delta 注入、nested memory 去重、post-compact 重建，以及失败时的 blocking/reactive fallback。"
/>

默认不是 vector 检索系统，也没有 embedding 冲突更新。它处理的是 message/context 的工程预算；memory 里的 recall、remember、dedup 是另一套主题。读这段源码时，最重要的是看每一层为什么放在这个顺序，而不是只记住“有 compact”。
